# Technical review of the supplied snapshots

This review records source-level findings, not newly executed HDL tests. The original electrical/logic behavior was not modified. Relative paths below are within `snapshots/<snapshot>/rtl/` unless otherwise indicated.

## Snapshot identity

| Repository name | Original folder | Interpretation |
| --- | --- | --- |
| `hazard` | `ARM968E_S_Hazard_Only` | Integrated pipeline with dependency stalls |
| `forwarding` | `ARM968E_S_Forwarding` | Adds forwarding unit, operand muxes and runtime enable |
| `sram` | `ARM968E_S_SRAM` | Forwarding pipeline with SRAM controller/model |
| `sram-alternate` | `ARM968E_S/ARM968E_S` | Another SRAM integration, not a baseline |

Four directories do not imply four independently preserved chronological phases. The foundation is present as modules in the integrated designs. The generic-name SRAM variant differs in `ARM.v`, `SRAM_Controller.v` and `SRAM_Simulator.v`; their exact changes are in [sram-variant.diff](sram-variant.diff). The archive does not establish a reliable development order between these two variants.

## Forwarding selection is coupled across operands

Affected: `forwarding`, `sram`, `sram-alternate`, file `forwarding_unit.v`.

`mem_check` is the OR of the two MEM destination comparisons. An outer `if(mem_check) ... else if(wb_check)` selects one stage for both operands before independently checking the write enables.

For example, with `src1=1`, `src2=2`, `MEM_Dest=1`, `WB_Dest=2`, both write enables and `FW_EN` high, the RTL selects MEM for source 1 but leaves source 2 at its original value. Source 2 needs WB. A matching MEM destination with `MEM_WB_EN=0` can also suppress a valid WB selection. Priority must be resolved independently for each operand, using valid/write-enable qualifiers.

## Store data bypass is absent

Affected: all forwarding-capable snapshots, file `ARM.v`.

The EXE/MEM register captures `EXE_Val_Rm_i` for store data, although `Forward_Val2` is available. A producer followed by a dependent store can therefore use stale data when the forwarding-enabled hazard policy permits the store to advance. This requires a directed register-to-store regression, including a load producer.

## Source-use decoding needs explicit tests

Affected: integrated snapshots, file `ID_Stage.v`.

`Two_src = ~(uncond_MEM_R_EN | imm)` uses instruction bit 25 as a broad source-use qualifier. Any accepted store encoding with that bit high suppresses the second-source comparison even though the store still consumes a data register. The bundled memory offset generator separately selects sign-extended 12-bit offsets for all memory operations. Define the accepted memory encodings explicitly rather than assuming all ARM addressing forms are supported.

The first source is always compared, including operations that may not consume Rn. This may add unnecessary stalls. Condition evaluation uses the status register in ID, while status updates occur at the falling edge; flag dependencies and branch/stall overlap need directed coverage.

## Arithmetic, shifts and conditions

These expressions occur in the supplied shared datapath modules. They are sufficient to limit ISA claims without asserting that the supplied program exercises every defect.

| Location | Source observation | Consequence / example |
| --- | --- | --- |
| `ALU.v` | `SUBC_result = SUB_result - {32{~c_in}}` | With `c_in=0`, the subtrahend is `0xffffffff`, not one. For operands 10 and 3, the low 32-bit result is 8 rather than 6 for subtraction with a borrow of one. |
| `Val_2_Generator.v` | `Val_Rm >>> Shift_operand[11:7]`, with `Val_Rm` declared unsigned | The arithmetic-right-shift path does not sign-extend a negative 32-bit operand. |
| `cond_check.v` | LE case uses `Z & (N ^ V)` | It rejects equality when `Z=1` and `N=V`; the intended signed less-than-or-equal predicate requires OR. |
| `ALU.v` | Carry derives from extended subtraction results; logical operations force C/V to zero | Carry/borrow and flag-update semantics require an explicit specification and boundary tests. |

The processor uses a word-indexed PC, simple R0–R15 storage, a restricted decoder and a bundled ROM program. No evidence establishes Thumb support, exceptions, privileged execution, a complete ARM memory model or drop-in binary compatibility.

## SRAM address truncation

Affected: `sram`, file `SRAM_Controller.v`.

IDLE and BYTE0 use `cpu_addr[8:0]`, but BYTE1 and BYTE2 use `cpu_addr[6:0]`. For word index 128, the generated byte addresses are 512, 513, 2 and 3 instead of 512–515. The alternate snapshot uses `[8:0]` for all four byte addresses, resolving this particular inconsistency.

## Extra SRAM write state

Affected: both SRAM variants, file `SRAM_Controller.v`.

`sram_we_n` is continuously `!cpu_mem_write`. In BYTE3, `sram_cs_n` remains low while `sram_addr` and `write_byte_buffer` retain their combinational defaults of zero. With a held store request, the synchronous memory therefore receives another enabled write to byte address zero in this state. Write strobes should be scoped to the intended byte transfers and validated against the memory clock edges.

## Missing memory clock and memory-enable differences

Affected: `sram-alternate`, files `ARM.v` and `SRAM_Simulator.v`.

The `SRAM_Model` declaration has a `clk` input, but its named-port instance omits that connection. Its XPM memory cannot perform the intended synchronous operations from this top-level connection.

The alternate also ties XPM `ena` and `regcea` high rather than qualifying them with `CS_n`. Combined with a write enable driven directly by the CPU request, this can permit writes outside chip-selected transfer states. Its output driver adds a `WE_n` qualifier, but that change does not repair the clock or write-enable problems.

## Memory stalls and state updates

The SRAM variants freeze all four pipeline registers when `cpu_ready=0`; PC and IF/ID additionally respond to dependency hazards. The register file and status register do not have a corresponding memory-stall enable. Held writeback/status controls can therefore cause repeated updates. `register_pipe` gives freeze priority over flush, so a branch flush during a freeze is deferred. These interactions require tests spanning memory waits, branches, flag consumers and back-to-back transactions.

## Evidence limits

The testbenches drive clock, reset and, where applicable, forwarding enable, then call `$stop`. They do not compare register/memory outputs with expected values. The common ROM contains 47 initialized words, including arithmetic, conditional operations, memory access and loops; no assembly source or reference execution trace was supplied.

Archived elaboration logs end with a built simulation snapshot. Archived simulation logs do not contain a correctness verdict. Some simulation databases and hardware captures are present in the original archive, but they were not decoded or used to infer numerical speedups.

Implementation timing and utilization were extracted from the supplied Vivado 2018.3 outputs. Their build dates and source versions cannot be tied to the packaged RTL by a verified build manifest. Treat those values as historical implementation evidence. In particular, historical elaboration success does not override the missing-clock connection visible in the alternate source.

## Packaging changes and reproduction

RTL, VHDL, testbenches and user constraints are byte-identical to their source files; hashes are in `results/source-manifest.json`. XCI coefficient-file references were relocated to the packaged `memory/output.coe`. Vivado caches, generated IP output products, binary wave databases, checkpoints and bitstreams are excluded.

The reconstruction helper imports the preserved IP configurations into a clean project and regenerates targets. It has not been run in Vivado. No RTL fixes, new clock constraints, vendor-IP migration or new functional verification results are included.
